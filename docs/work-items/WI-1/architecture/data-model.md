## 0. Provider-neutral domain concepts (R-140, R-288)

The nine concepts of PD-14 and how they are held. Their shared schemas live in `packages/contracts/src/domain/` (Zod, T20) and are the only shapes downstream stages see (R-059). No concept carries a provider field name, code or identifier; the only provider-specific value that core code holds is the opaque `SourceRef` (AD-21), which it stores and passes back to the adapter unchanged and never parses.

| Concept | Domain shape (shared schema) | Held in |
|---------|------------------------------|---------|
| Competition | catalogue ID (slug), display name, area name or null, reference marker, bindings to one or more sources (`sourceId`, opaque `competitionRef`) | in memory (catalogue service, rebuilt from sources and `config/catalogue.json`); `projects.competition_id` and name snapshot |
| Season | slug ID given by the adapter, label, current flag, start and end dates or null, `startYear` or null (for counterpart resolution), opaque `seasonRef` | in memory (cached listing); `projects.season_id` and label snapshot |
| Stage | slug ID given by the adapter, name as the source gives it, order, standings expectation (`expected`, `not_expected`, `unknown`), matchday numbers (possibly none), whether it is selectable as a whole | in memory (cached listing); `projects.stage_id` and label snapshot |
| Matchday | a number inside a stage; a selection is a stage plus a matchday number or the whole stage (AD-24) | `projects.matchday` (nullable) |
| Match | source match key, home and away team keys, kickoff, provider-neutral status (`scheduled`, `in_play`, `finished`, `postponed`, `suspended`, `cancelled`, `abandoned`, `awarded`), score or null, reference | `observations` (per fact key), `facts` |
| Team | source team key, name; canonical team ID after identity matching (AD-18) | `teams`, `team_aliases`, facts |
| Standing | table "as of" time and rows (position, team, played, won, drawn, lost, goals for and against, goal difference, points), or an explicit unavailability reason | `observations`, `facts`; unavailability on the run (`workflow_runs.standings_availability`) |
| Source | configured descriptor: ID, name, data mode, adapter kind, role, acceptance, independence group, official-publication flag, publication permission, enabled | `sources` (upserted from configuration), `workflow_runs.config_snapshot` |
| Verification status | `verified`, `unverified` with reason (`awaiting_independent_verification`, `disputed`, `no_accepted_source`, `team_identity_unmatched`), `manually_approved` (OD-17) | `facts.status`, `facts.unverified_reason`; `manually_approved` is the effective status derived from `manual_approvals` |

Provider-specific extensions stay out of these schemas: an adapter may keep its own allow-list response schemas and mapping types inside its adapter directory, and anything it must remember about a competition, season, stage or selection goes into its opaque `SourceRef` (a JSON string of at most 512 characters that only the issuing adapter interprets).

## 1. Storage layout

| Store | Location | Content |
|-------|----------|---------|
| Database | `<dataDir>/edr.sqlite` (WAL mode, `foreign_keys=ON`) | every record below |
| Rendered slides | `<dataDir>/renders/<projectId>/<elementVersionId>.png` | PNG per slide version; SHA-256 stored in `element_versions` |
| Exports | `<dataDir>/exports/<projectId>/<exportId>/` | `01.png` ... `NN.png`, `caption.txt`, `manifest.json`; hashes in `export_files` |
| Brand assets | `<dataDir>/brand-assets/<assetId>.<png or jpg>` | operator-registered brand files; SHA-256 in `brand_assets` |
| Import originals (T11G) | `<dataDir>/imports/<importId>/original.<json or csv or form.json>` | the original content of an applied MANUAL_DATA import, byte for byte: for file channels exactly the bytes received in `contentBase64` after strict base64 decoding, including any BOM and CRLF line ends (T11H-F01); for form entry the submitted document serialized once as canonical UTF-8 JSON, size-checked against 512 KiB before anything is written (T11H-F10); `imports.original_sha256` is the SHA-256 of exactly these bytes and therefore equals the hash of the operator's file (R-066, R-277). Written with the exclusive flag under a realpath-checked UUID path; downloaded under a server-generated name (T11H-F11) |
| Provider projection cache (T11G) | process memory only | mapped, validated domain projections with retrieval time and expiry; never written to disk (AD-27) |

`<dataDir>` defaults to `data/` in the repository root (git-ignored) or `EDR_DATA_DIR`. Every file path stored in the database is relative to `<dataDir>` and built from generated IDs only.

## 2. Conventions

- Tables are SQLite `STRICT` tables. IDs are `TEXT` UUIDs generated by `crypto.randomUUID()`, except catalogue, season, stage and team-key slugs and configured source IDs. Times are `TEXT` ISO-8601 UTC with milliseconds (`2026-10-27T16:32:21.123Z`). JSON columns are `TEXT` validated by Zod on write and read, with `CHECK (json_valid(col))`.
- Enumerations are `TEXT` with `CHECK (col IN (...))`.
- Rows are never deleted (OD-08). Superseded or invalidated rows carry a timestamp column instead.
- Migrations: `apps/server/migrations/NNNN_<name>.sql`, applied in order in one transaction each by the migration runner at startup, recorded in `schema_migrations`. The full MVP schema, including the T11G tables and columns, is migration `0001_initial.sql`, created by T18 (owner of `apps/server/migrations/**` and `apps/server/src/platform/db/**`; T10-F21). No code exists yet, so the T11G changes are part of `0001_initial.sql`, not a second migration. A later schema change is a new migration and a decision above LOW (schema change); applied migrations are never edited. Migrations:
  - `0001_initial.sql` (T18): the full MVP schema of sections 3 and 4.
  - `0002_qa_capitalized_tokens.sql` (T56, OD-56): rebuilds `qa_results` so that `check_name` also accepts `capitalized_tokens` (OD-26, OD-38); SQLite cannot alter a CHECK constraint, so the table is created anew, every row copied unchanged, the old table dropped and the new one renamed, inside the runner's transaction and foreign-key check (no table references `qa_results`). Every other column, constraint, the UNIQUE and STRICT are unchanged.
- SQL access (T10-F14): the `Db` port exposes prepared statements with bound parameters only; dynamic identifiers (column or sort names) come from code constants, never from input; a lint rule rejects template literals containing `${` passed to `prepare` or `exec`.
- Guard atomicity (T10-F15): every approval, final-approval, export, manual-approval and import-application guard check and the write it protects run in one synchronous `BEGIN IMMEDIATE` transaction on `DatabaseSync`, with no `await` inside.
- Failure reasons (T10-F10): `failure` columns hold a JSON object `{ code, sourceId, path, httpStatus }` with `code` from the closed list of the contract schema `Failure` (T11G adds `access_refused`, `not_available`, `bad_request`); never a provider body, an exception message, a credential or a file path.
- Files (T10-F13): the data directory is created with mode 0700; new files are created with the exclusive flag (`wx`), never overwritten; IDs are checked against the UUID pattern before any path is built (also when read back from the database); containment is checked against `fs.realpath(dataDir)`.
- Catalogue data (competitions, seasons, stages) comes from the configured sources at run time and from `config/catalogue.json` links; it is not stored in tables, except the snapshot a project keeps of its own selection (section 3.1) and the MANUAL_DATA imports (section 3.5). Templates and languages live in configuration and code.
- Opaque source references (AD-21): `selection_ref` and the `*_ref` columns hold adapter-owned JSON strings (at most 512 characters, `json_valid`); only the adapter of the row's `source_id` interprets them; no SQL query, stage or route reads inside them.

## 5. Excluded data (R-112, R-113, R-119, R-233, R-280)

- No table, column or JSON field holds player-level or other person information (player names, goal scorers, line-ups, cards, player statistics, referees, coaches, squads). Provider schemas are allow-lists (`contracts/provider-ports.md` section 1); unknown and person fields are dropped at the adapter before the projection cache, persistence or logging. Manual imports with a person-level field are rejected naming the field, so a preserved original never holds person data (R-119).
- No user, account, credential, session or operator-identity entity exists. No personal data of the operator is stored.
- No secret is stored (`workflow_runs.config_snapshot` holds adapter IDs and options without credentials; `FOOTBALL_DATA_API_TOKEN` is never read into the configuration object, AD-30). No raw provider payload, response header or request URL with query values is stored (AD-27, AD-34).
- T18 adds an automated schema test that lists every table and column through `sqlite_master` and `pragma_table_info` and fails on any name matching `player|scorer|lineup|line_up|referee|coach|squad|user|account|password|session|email|login|token|secret` (R-233), and T45 confirms it in the conformance review.

## 6. Traceability chain (R-044, R-221, R-287)

`exports -> export_files (element_version_id) -> element_versions -> element_fact_refs -> facts -> fact_evidence -> observations -> retrievals -> sources`, plus `observations.import_version_id -> manual_selection_versions -> imports` (original content and its hash) for MANUAL_DATA, `manual_approvals` for MANUALLY_APPROVED facts, `disputes` for disputed or resolved facts, `projects.source_id` and `data_mode` for the source chosen, and `workflow_runs.config_snapshot` for the source configuration in force. The export `manifest.json` repeats the element version IDs, fact IDs, data mode and source IDs per file, so that an exported folder can be traced back even when opened outside the application.

## 7. Retention

Everything is kept locally without expiry; there is no deletion function (OD-08). Superseded drafts, versions, manual selection versions, import originals, revoked manual approvals and invalidated final approvals remain readable for history (R-043, R-220, R-068). The provider projection cache is in memory and disappears with the process.
