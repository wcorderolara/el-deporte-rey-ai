## 2. Architecture summary

The platform is a local-first web application for a single operator (PD-05; `architecture.md` section 1). One Node.js process listens on `127.0.0.1` only and serves the web UI and a JSON HTTP API. It runs the content workflow in process and keeps its data in one SQLite file plus a local data directory. External providers are reached only through configured adapters and the egress client.

- Workflow (AD-10): research, verification, content, rendering and visual QA, followed by operator review, per-item approval, final approval and export. There is no publication function (BR-11). Only the content stage uses AI (AD-08). The other stages are deterministic (AD-07, AD-11, AD-12).
- Data acquisition modes (PD-13): LIVE_DATA comes from an external provider; the first adapter is FootballDataProvider (PD-12). MANUAL_DATA comes from operator imports in JSON, CSV or a web form, through ManualDataProvider and `modules/imports`. DEMO_DATA comes from synthetic fixtures through FixtureDataProvider and is the default for development, tests and demonstrations. All three sit behind one ingestion port and produce one provider-neutral domain representation (AD-21, AD-22). The competition catalogue is discovered from the enabled sources at run time; no competition is fixed in code (PD-14, BR-15, AD-23).
- Boundaries: `modules/*` depend on `platform/*`, the `providers/*` ports and `workflow`. `providers/*` depend only on `platform/net` and `platform/config`. Only `platform/net` opens network connections. Provider identifiers appear only in adapters, `apps/server/scripts`, `config` and `fixtures` (AD-31).
