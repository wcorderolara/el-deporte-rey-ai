## 2. Architecture summary

The platform is a local-first web application for a single operator (PD-05; `architecture.md` section 1). One Node.js process listens on `127.0.0.1` only and serves the web UI and a JSON HTTP API. It runs the content workflow in process and keeps its data in one SQLite file plus a local data directory. External providers are reached only through configured adapters and the egress client.

- Workflow (AD-10): research, verification, content, rendering and visual QA, followed by operator review, per-item approval, final approval and export. There is no publication function (BR-11). Only the content stage uses AI (AD-08). The other stages are deterministic (AD-07, AD-11, AD-12).
- Data acquisition modes (PD-13): LIVE_DATA comes from an external provider; the first adapter is FootballDataProvider (PD-12). MANUAL_DATA comes from operator imports in JSON, CSV or a web form, through ManualDataProvider and `modules/imports`. DEMO_DATA comes from synthetic fixtures through FixtureDataProvider and is the default for development, tests and demonstrations. All three sit behind one ingestion port and produce one provider-neutral domain representation (AD-21, AD-22). The competition catalogue is discovered from the enabled sources at run time; no competition is fixed in code (PD-14, BR-15, AD-23).
- Boundaries: `modules/*` depend on `platform/*`, the `providers/*` ports and `workflow`. `providers/*` depend only on `platform/net` and `platform/config`. Only `platform/net` opens network connections. Provider identifiers appear only in adapters, `apps/server/scripts`, `config` and `fixtures` (AD-31).

## 6. Interface contracts

The declared contracts, their status, recorded hashes and frozen snapshots are in the project configuration (`contracts`). List here the interface conventions (naming, versioning, error format, compatibility policy):

- Status: no contract is declared yet (`contracts: []`). The `http-api` proposal is `contracts/http-api.openapi.yaml` in the WI-1 architecture directory, at `1.0.0-proposed.2`, accepted as a pre-release revision (OD-14, OD-23; one additive QA check value by OD-26). T20 promotes it to `contracts/http-api.openapi.yaml` (`1.0.0`), T25 declares it, and T26 records its hash here. Only `http-api` is declared; `contracts/provider-ports.md` stays an internal architecture interface (AD-20).
- HTTP conventions: `architecture-delta.md` section 2.1. Base path `/api/v1`. JSON with camelCase fields and ISO-8601 UTC times. Server IDs are lowercase UUIDs; catalogue and template IDs are slugs. Every ID has a `pattern` and every request string a `maxLength`. Request and response objects are closed. Errors are `application/problem+json` with a stable `code` from a closed list, and a `detail` built only from fixed text and sanitized parameters.
- Local request protection is part of the contract (AD-14): 421 for a Host outside the allow-list on every operation; `X-EDR-Client: web`, an allowed `Origin` (`null` refused) and a JSON content type on every method other than GET and HEAD; 403 declared on every operation, 415 on every mutating operation, and 413 where a body exists. GET and HEAD have no persistent side effects.
- Versioning and compatibility (PD-11): within `v1` only additive changes are allowed. A breaking change needs a new major path and a Product Owner decision (HIGH-06). Every change to the declared contract follows the framework's contract-change process with a Contract Safety assessment (CS-1 to CS-5).
- Shape authority (AD-04): the OpenAPI document is authoritative. `packages/contracts` mirrors it with Zod schemas, and the contract tests check parity and conformance.
- Provider neutrality (PD-14, BR-15; `architecture-delta.md` section 11.2; `contracts/provider-ports.md` section 1):
  - The data mode is the closed enum `LIVE_DATA`, `MANUAL_DATA`, `DEMO_DATA`.
  - No contract schema, field, enum or example names a provider or carries a provider field name, code or identifier (R-288).
  - Provider references are opaque `SourceRef` strings of at most 512 characters, interpreted only by the issuing adapter and never parsed, compared or logged by core code (AD-21).
  - Attribution references use the prefixes `source:`, `fixture:` or `import:`, are never URLs, and are shown as text only (AD-36).
  - Catalogue IDs are `<sourceId>-<localKey>` slugs or configured link IDs, and are never merged by name.
  - Provider identifiers (competition codes and IDs, hostnames, provider names) appear only in `apps/server/src/providers/sports/adapters/**`, `apps/server/scripts/**`, `config/**` and `fixtures/**`, enforced by the lint rule of AD-31.
  - Credentials never appear in any schema (SC-06).

## 7. Quality gates

The gates, their commands, pass conditions and applicability are in the project configuration (`gates`); the gate model is the framework's quality-gates workflow. List here only project notes about running them (disposable resources, ports, long runs):

- Configured today: only the framework-mandatory gates. The project gates `PRJ-INSTALL` to `PRJ-AUDIT` are planned in `architecture-delta.md` sections 7.2, 7.3, 11.7 and 11.13.4 (commands, paths, timeouts) and are added by T25. T26 completes these notes for the configured gates.
- Ports (`architecture.md` section 12), all on `127.0.0.1` with `strictPort`: 4300 for local use and the development API, 5173 for the Vite development server, 4310 for e2e and accessibility gate runs in the verify worktree, and 4320 for the Product Owner demonstration in the demo worktree.
- Disposable data: tests and gate runs use temporary data directories and configurations generated from `fixtures/config/`, removed after the run. They never use `data/` or the committed configuration's data directory.
- Network for tooling: `PRJ-INSTALL` (`npm ci`) and `PRJ-AUDIT` (`npm audit`) need the npm registry. The first `PRJ-E2E` or `PRJ-A11Y` run downloads Chromium into `.cache/ms-playwright`. This is tooling access, not product access (R-222). A failure caused by missing access is an environment issue (AR-04). Product code under test has no external network: the Vitest network guard fails any non-loopback connection (R-241).
- Credentials: no gate uses `FOOTBALL_DATA_API_TOKEN` or reaches a sports-data provider. The default test setup deletes `FOOTBALL_DATA_API_TOKEN` and `EDR_LIVE_TESTS`, and the e2e runner does not forward them (R-257, R-258, AD-30).
- Manual only, never a gate (AD-32): `npm run test:live` (skipped unless `EDR_LIVE_TESTS=1` and the token are set; at most 5 requests) and `npm run probe:football-data` (run by the Orchestrator in T53 only under the SC-08 conditions).
- Long runs: `PRJ-E2E` (1200 s) and `PRJ-INTEGRATION` (900 s) have the longest planned timeouts. `PRJ-INSTALL` runs first so the later gates have `node_modules`.
